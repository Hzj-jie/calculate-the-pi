# Calculating the Value of π - Arbitrary-Precision Arithmetic - big_uint.adaptive_array

Although this might seem almost too minor to mention, it is still worth a brief explanation. [service/math/big_uint/big_uint.adaptive_array.vb](https://github.com/Hzj-jie/osi.net/blob/master/service/math/big_uint/big_uint.adaptive_array.vb) is a data structure similar to `vector`—a dynamically resizing array. The implementation of [root/formation/vector.vb](https://github.com/Hzj-jie/osi.net/blob/master/root/formation/vector.vb) is based on the exact same underlying structure. `adaptive_array` itself is generated by [root/codegen/adaptive_array](https://github.com/Hzj-jie/osi.net/tree/master/root/codegen/adaptive_array); this was a very early implementation, otherwise `root/codegen/precompile` would have been used instead. Of course, that doesn't really matter now—this data structure is relatively stable and rarely changes. The most recent modifications were all aimed at improving the performance of `big_uint`.

The main reason for using `adaptive_array` directly instead of `vector` is performance.

First, `vector` is a generic (template) class, and generics incur a performance overhead in .NET. For details, see [root/tests/connector/generic_perf.vb](https://github.com/Hzj-jie/osi.net/blob/master/root/tests/connector/generic_perf.vb), which benchmarks common generic operations. Running this test yields comparative numbers showing that reading and writing values in `generic_class(Of Int32)` is about 8% slower than in `int_class`. While this 8% figure varies across .NET versions, it is safe to assume that generic types are slightly less efficient than non-generic ones.

Second, most `vector` operations include additional assertions for safety. For example, [get and set](https://github.com/Hzj-jie/osi.net/blob/master/root/formation/vector.vb#L57) verify that accessed elements are within bounds and copy the data rather than returning a reference.

Arbitrary-precision arithmetic demands very high performance. For instance, on a very slow machine (the fast machine is reserved for writing code), computing the first 81,655 digits of $e$ took about 2 minutes and 30 seconds; a 10% performance drop would add 15 seconds. Therefore, using code generation to produce a specialized `big_uint.adaptive_array.vb` tailored for `big_uint` is completely reasonable.

Beyond that, there isn't much else to say—the extensive use of `aggressive_inlining` is likewise driven by performance considerations.
